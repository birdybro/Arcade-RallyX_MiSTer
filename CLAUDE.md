# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

FPGA simulation model of the Namco/Midway **New Rally-X** (1981) arcade hardware, packaged as a MiSTer core for the DE10-Nano (Cyclone V). It cycle-models the original Z80-based board (CPU, custom video/sprite/sound hardware) in HDL. The original implementation is by MiSTer-X; this fork wraps it in the standard MiSTer framework.

## Building

This is a Quartus FPGA project, not a software project — there are no tests, lint, or run commands. The build product is an `.rbf` bitstream.

- Open `Arcade-RallyX.qpf` in **Intel Quartus Prime 17.x** (the version pinned by the IP cores).
- Compile the project (top-level entity is `sys_top`). Output lands in `output_files/`.
- `clean.bat` removes Quartus-generated intermediates (`db/`, `incremental_db/`, `output_files/`, etc.).
- There is no command-line build wrapper checked in; compilation is done through the Quartus GUI or `quartus_sh --flow compile Arcade-RallyX`.

To run on hardware you also need the matching `.mra` and a MAME-named ROM zip (`nrallyx`) — ROMs are **not** in this repo. See `README.md` for MiSTer install steps.

## Source file organization

- **`sys/`** — the unmodified MiSTer framework (HPS interface, video scaler/scandoubler, audio out, PLLs, top-level `sys_top.v`). Treat as a vendored library; do not edit when working on the game. It is shared verbatim across all MiSTer arcade cores.
- **`rtl/`** — the game-specific core (see architecture below).
- **`Arcade-RallyX.sv`** — the `emu` module: the seam between `sys/` and `rtl/`. Wires HPS I/O, controls, video/audio, ROM download, hiscore, and pause to the game core.
- **`files.qip`** — the authoritative source-file list for the game. **Add new RTL files here**, not to the `.qsf` (the `.qsf` just `source`s `files.qip`).
- **`releases/`** — built `.rbf` bitstreams and the `.mra` ROM-assembly descriptors.

## Architecture

The signal flow is `sys_top` (framework) → `emu` (`Arcade-RallyX.sv`) → `fpga_NRX` (`rtl/fpga_nrx.v`, the game board) → video/sound/CPU submodules.

**`fpga_NRX` (`rtl/fpga_nrx.v`) is the board top.** It instantiates the Z80 and does all CPU address decoding. Key facts:
- Clocks derive from a single 24.576 MHz input: CPU runs at 3.0 MHz (`CCLK = _CCLK[2]`), with a x2 phase at 6.0 MHz.
- The Z80 is the **T80** soft core (VHDL, `rtl/cpu/T80*.vhd`), instantiated as `T80s`.
- Memory map is decoded inline as `wire` comparisons on the address bus (`ad`): ROM `$0000–3FFF`, work RAM `$9800–9FFF`, inputs `$A000–AFFF`, sound regs `$A100–A1FF`, and a latch block at `$A180` (smoke/"bang", interrupt enable, screen flip, lamps).
- The data bus is a wired-OR of per-region read terms (`idt = romd | ramd | irqv | vidd | inpd`) gated by their chip-enables — there is no tristate bus.
- Interrupts: vertical blank latches an IRQ; the CPU acks via the `$A181` interrupt-enable write; the interrupt vector is captured from an I/O write (`iowr`).

**Video** — `NRX_VIDEO` (`rtl/nrx_video.v`) + `NRX_SPRITE` (`rtl/nrx_sprite.v`). Renders tilemap, the radar/"dot" layer, and sprites. Pixel timing/blanking is generated by `HVGEN` inside `Arcade-RallyX.sv` (a 288-wide, ~224-line raster) and fed back into the core as `HP`/`VP` position inputs — the core is a position-driven renderer, not a free-running framebuffer.

**Sound** — `NRX_SOUND` (`rtl/nrx_sound.v`) is the Namco 3-channel WSG (wavetable) synth, plus `nrx_bang.v`, a netlist-derived model of the explosion/smoke "bang" noise (replacing an older sampled version — see commit `abd3c38`). Output is unsigned 8-bit PCM, zero-extended to 16-bit in `emu`.

**ROM loading** — there is no SDRAM; all game ROMs are loaded into on-FPGA block RAM during HPS download. The `.mra` concatenates the MAME ROMs into one stream; each `DLROM`/RAM instance self-selects its slice by decoding the high bits of the download address `ROMAD`. Current map (see `releases/rommap.txt`):
  - `0000–3FFF` CPU code → `cpurom` (`ROMAD[15:14]==00`)
  - `4000–4FFF` char/object patterns → `chrrom` (`ROMAD[15:12]==4`)
  - `5000–50FF` radar dot pattern → `dotrom` (`ROMAD[15:8]==50`)
  - `5100–51FF` sound waveforms → in `nrx_sound` (`ROMAD[15:8]==51`)
  - `5200–52FF` color lookup → `colorlt` (`ROMAD[15:8]==52`)
  - `5300–531F` palette → `palette` (`ROMAD[15:5]==5300x`)
If you change ROM layout, the `DLROM` address-decode constants, `rommap.txt`, and the `.mra` `<rom>` offsets must stay in sync.

**Shared MiSTer subsystems** wired in `emu`: `hps_io` (OSD menu via the `CONF_STR` string, controls, ROM/NVRAM transfer), `arcade_video` (scaling/aspect), `pause` (CPU pause on OSD/idle), and `hiscore` (`rtl/hiscore.v`, NVRAM save/load of the high-score table, gated through the `hs_*` ports on the core).

## Conventions specific to this core

- The on-screen menu and DIP layout live in the `CONF_STR` localparam in `Arcade-RallyX.sv`; DIP switches arrive as `ioctl_index==254` writes and are inverted before reaching the core (`.DSW(~dips)`).
- Controls are active-low at the board (`iCTR1`/`iCTR2` are bit-inverted). Per the comment in `emu`, controller-1 bit 0 is the hardware service line, and DIP bit 0 ("Service Mode"/freeze) is partly handled in hardware, not via the DIP register.
- Game logic edits belong in `rtl/`; framework behavior lives in `sys/` and should generally be updated by syncing from upstream MiSTer rather than hand-editing.
